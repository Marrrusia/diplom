# Интеллектуальный анализ покрытия требований

Настольное приложение для Windows 11, Python 3.11+ и PySide6.
Этапы 1–5: импорт, выделение элементов, анализ покрытия и генерация тестов.
Полное редактирование результатов, SQLite и экспорт пока не реализованы.
Импорт доступен в разделах «Требования» и «Тест-кейсы»; остальные разделы — будущие функции.

## Структура

```text
main.py                  — запуск из PyCharm
pyproject.toml           — зависимости и конфигурация pytest
reqtest/
  main.py                — точка входа, журналирование
  ui/main_window.py      — главное окно с семью разделами
  models/domain.py       — требования, элементы, тесты, связи, проект, настройки
  models/demo.py         — ручной пример требования CRC
  services/              — будущий анализ, генерация, валидация
  llm/                   — будущие OpenAI-совместимый API и Ollama
  storage/               — будущее хранение SQLite
  importers/             — будущие TXT, DOCX, XLSX, CSV
  exporters/             — будущий XLSX-отчёт
tests/                   — проверки моделей и окна
```

## Запуск в PyCharm на Windows 11

1. Установите Python 3.11 или новее с python.org и PyCharm.
2. Откройте каталог проекта `diplom` через File → Open.
3. В Settings → Project → Python Interpreter добавьте локальную среду Virtualenv
   в `.venv`, выбрав установленный Python 3.11+.
4. В терминале PyCharm выполните:

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe main.py
```

Можно запустить `main.py` через контекстное меню Run. Рабочий каталог
конфигурации запуска — корень проекта; интерпретатор — `.venv`.
Если среды ещё нет, создайте её командой `py -3.11 -m venv .venv`.
Для этой версии сервер LLM и API-ключ не нужны; платные сервисы не требуются.
Каталог журнала можно переопределить переменной `REQTEST_LOG_DIR`.
Журнал приложения: `%USERPROFILE%\.reqtest\logs\application.log`.

## Linux / облачная среда

```bash
python -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest
.venv/bin/python main.py
```

На Linux без дисплея используйте `QT_QPA_PLATFORM=offscreen` только для
проверок, а не для интерактивной работы. Поддержка Windows предусмотрена,
но выполнение тестов на Linux не заменяет проверку на Windows 11.

## Инварианты и ограничения

Модели запрещают неизвестные поля, проверяют идентификаторы, ссылки,
диапазон уверенности и точное наличие цитаты элемента в требовании.
Проверка цитаты не доказывает семантическую достоверность описания:
это задача следующих этапов и ручной проверки.
`CoverageLink.confirmed` учитывает только явно принятое покрытие;
агрегирование покрытия и исключение отклонённых тестов реализуются отдельно.
Для изменения коллекций проекта создавайте новый снимок через
`Project.model_validate(data)`: изменение списка на месте не запускает
валидацию Pydantic.
Ключ LLM существует только в настройках сеанса, скрыт в repr и исключён
из сериализации. Постоянное безопасное хранение ключа пока отсутствует.

`demo_project()` создаёт четыре проверяемых аспекта примера
`SDD_MVA_INIT_F_00040`. Это ручная демонстрация структуры, не анализ LLM.
Поведение при `Instance != CRC` не задано и не добавляется.

## Этап 2: импорт

Сначала загрузите требования, затем тесты. Данные пока хранятся в памяти:
закрытие окна удаляет результаты импорта (SQLite — этап 8).
Кнопка «Исправить текст выбранного требования» позволяет устранить ошибки.

TXT: UTF-8; блоки разделяются пустой строкой или новой строкой `ID: текст`.
Без ID назначаются REQ-0001 и далее. Строка вида `Слово: текст` трактуется
как начало требования, поэтому не используйте такой формат для продолжений.
DOCX: тот же формат абзацев; таблицы — без заголовка, две колонки ID | текст.
Для сложной структуры документа предварительно приведите его к этому формату.

XLSX: первая непустая строка — уникальные непустые заголовки; выберите лист
и сопоставьте колонки. Требования: обязательны ID и текст, тип и источник
необязательны; несопоставленные колонки сохраняются в metadata.
Формулы отклоняются: предварительно замените их вычисленными значениями.

CSV/XLSX тестов: обязательны ID, требование, название, действия, ожидаемый
результат. Предусловия и входные данные необязательны. Действия и предусловия
разделяются переводами строк внутри ячейки. Входные данные — обычный текст
или JSON-объект со строковыми значениями. CSV: UTF-8 (с BOM или без) или
Windows-1251; разделители запятая, точка с запятой, табуляция определяются
автоматически. CSV с многострочными ячейками должен использовать кавычки.

Импортированные тесты имеют источник «существующий», статус «ожидает
проверки». Неизвестное требование, дубликат ID или некорректная строка
отменяют весь импорт; ранее загруженные данные сохраняются. Не загружайте
один и тот же набор дважды. Примеры: `examples/requirements.txt`,
`examples/requirements.xlsx`, `examples/requirements.docx`,
`examples/test_cases.csv`, `examples/test_cases.xlsx`.

## Этап 3: LLM и выделение проверяемых элементов

### Бесплатный локальный вариант: Ollama на Windows 11

1. Установите Ollama: https://ollama.com/download/windows .
2. В PowerShell скачайте модель (интернет нужен для загрузки):

```powershell
ollama pull qwen2.5:7b
ollama list
```

Если команда не найдена, перезапустите терминал. Ollama обычно запускает
сервер автоматически. Если сервер не запущен, выполните `ollama serve`.
Модель 7B требует нескольких ГБ RAM; быстродействие зависит от CPU/GPU.
Можно выбрать другую установленную модель, например меньшую по размеру.

3. Запустите `main.py`. В «Настройки LLM» задайте:
   тип `ollama`, адрес `http://localhost:11434`, модель `qwen2.5:7b`.
   API-ключ для локального Ollama не требуется.
4. Загрузите `examples/requirements.txt`.
5. В «Проверяемые элементы» нажмите «Выделить элементы всех требований».

Для OpenAI-совместимого сервера выберите `openai`, задайте базовый адрес
API с `/v1` (например, `http://localhost:1234/v1`), название модели и,
при необходимости, API-ключ. Сервер должен поддерживать chat/completions
и response_format json_object. Бесплатный локальный сервер также допустим.
Ключ скрыт в интерфейсе, исключён из сериализации и не записывается в БД;
настройки действуют только до закрытия приложения.

Анализ выполняется в QThread. Импорт и исправление требований блокируются
на время анализа; остальные разделы интерфейса доступны. Отмена срабатывает
после текущего HTTP-запроса (таймаут чтения 180 секунд). При попытке закрыть
окно во время анализа запрос отмены отправляется, окно остаётся открытым:
закройте его ещё раз после завершения операции.

При ошибке проект не меняется. Проверяются строгая схема JSON, категории,
непустые описания/цитаты, точное присутствие цитат и дубликаты элементов.
Описание с существующей цитатой всё ещё может содержать ошибку модели:
все элементы имеют статус «ожидает проверки» и не подтверждают покрытие.
Замечания о недостаточности спецификации показываются под таблицей.
Повторный анализ заменяет все элементы и сбрасывает связи покрытия и
ссылки тестов на элементы; импортированные тесты сохраняются.
Исправление текста требования сбрасывает его устаревшие элементы и связи.
Ручная проверка/редактирование элементов будет реализована на этапе 6.

Для примера CRC ожидаются явно указанные условия вызова и Instance == CRC,
действие включения тактирования и ограничение «без аргументов».
Результат зависит от модели. Поведение при Instance != CRC не следует
генерировать: оно не задано исходным текстом.

Проверки протоколов используют подменённые HTTP-ответы. Реальное качество
модели и запуск на Windows 11 должны проверяться отдельно на вашем компьютере.

### Исправление пропущенного условия вызова

Для явно записанного «При вызове [подкомпонента/функции/метода] Имя»
проверяется наличие отдельного элемента «условие» с точной цитатой триггера
и именем функции в описании. При пропуске выполняется один повторный запрос
на полный исправленный результат; повторный пропуск отклоняет анализ
без изменения проекта. Проверка не доказывает полноту остальных элементов
и не добавляет поведения, отсутствующего в исходном тексте.

### Проверка отдельных условий, действий и ограничений

Перед запросом составляется список аспектов для поддерживаемых явных
формулировок: «При вызове ...», «если значение ... равно ...», действие
через «вызовом макроса Имя()», а также «без аргументов». Модель получает
этот список вместе с JSON-схемой. Проверяется, что каждый аспект присутствует
в элементе правильной категории. Упоминание «без аргументов» только в действии
не заменяет отдельное ограничение. Повторный ответ проверяется заново по
всему списку, чтобы модель не потеряла ранее найденные аспекты.
Если повторная попытка неполна, проект не изменяется и показывается список
пропусков. Новые элементы автоматически не подставляются.
Эта проверка охватывает указанные формулировки, не доказывает полноту
произвольного требования и не отменяет ручную проверку результата.
Полный текст обрезанной ячейки элементов доступен при наведении мыши.

## Этап 4: анализ покрытия и матрица

1. Импортируйте требования и существующие тесты, затем выделите элементы.
2. В «Матрица покрытия» нажмите «Анализировать покрытие».
3. Нажмите на ячейку: под матрицей появятся предложение модели, уверенность,
   обоснование, технические совпадения и цитаты тестовых действий/результата.
4. Проверьте тест и решение вручную. Для положительного решения нажмите
   «Подтвердить выбранное решение», чтобы оно стало подтверждённым покрытием.
   «Отклонить выбранную связь» исключает её из подтверждённого покрытия.

Каждая пара с одинаковым идентификатором требования анализируется отдельно
в QThread. Число запросов равно сумме числа элементов × числа активных тестов
для каждого требования. Это может занять время на локальной модели.
Отмена доступна в разделе «Проверяемые элементы», после текущего запроса.
Данные не сохраняются между запусками приложения — это по-прежнему этап 8.

Проверяются точные технические имена/числа, но совпадение слов не служит
доказательством. LLM учитывает исходное требование, связанные элементы,
предусловия, входы, действия и ожидаемый результат. Точные цитаты действий
и результата обязательны для положительного решения. Выдуманные цитаты
отклоняют весь запуск; отсутствие доказательств, уверенность ниже 0.8,
отсутствующие технические токены и поддерживаемые явные противоречия
понижают решение до «требует проверки». Порог 0.8 — эвристика, уверенность
модели не является статистически калиброванной вероятностью.
Поддерживаемые явные противоречия: отрицание заданного равенства поля
константе и аргументы вызова, явно заданного без аргументов. Это не полная
формальная проверка всех противоречий: семантический вывод требует человека.

Результат модели «покрыт» до ручного принятия отображается «требует проверки».
Состояние «требует проверки» нельзя сразу подтвердить как покрытие: сначала
уточните тест и повторите анализ (редактор тестов — этап 6). Отрицательное
предложение модели отображается «не покрыт», его обоснование также доступно.
Пары с разными ID требований считаются не покрывающими друг друга в этой
версии. Пары одного требования до анализа — «требует проверки».

Процент = число элементов с хотя бы одной принятой положительной связью /
число выделенных элементов. Пустой набор элементов — процент не определён.
Неподтверждённые/непокрытые элементы считаются отдельно от подтверждённых;
это число не означает, что все такие элементы заведомо не покрыты.
Отклонённые тесты и непринятые сгенерированные тесты не учитываются.
Повторный анализ заменяет решения и ручные подтверждения с предупреждением.
100% возможно только после явного принятия связей ко всем выделенным элементам
и не доказывает полноту исходной спецификации или полноту выделения элементов.

Автоматические тесты используют подменённые ответы LLM, включая пропуски
доказательств, выдуманные цитаты, отрицательное условие Instance != CRC,
отмену и работу матрицы в фоне. Реальный Ollama проверяется на вашем ПК.

## Этап 5: генерация тестов

В «Генерация тестов» выберите режим и нажмите «Сгенерировать тесты».
Настройки сервера и модели — прежние, в «Настройки LLM».

- «Первоначальный набор»: доступен, если в проекте вообще нет тестов.
  Сначала импортируйте требования и выделите элементы. Если тесты уже есть,
  используйте дополнение или откройте новый сеанс без импорта тестов.
- «Дополнение покрытия»: целевые элементы — все элементы без принятой
  положительной связи с активным тестом. Неподтверждённое покрытие не
  считается доказанным. Перед генерацией завершите ручную проверку матрицы.
  При полном подтверждённом покрытии запросов к модели не выполняется.

Запрос содержит исходное требование, все его элементы, целевые аспекты,
покрытые аспекты и ранее имеющиеся тесты, включая предложения и отклонённые
тесты для поиска повторов. Один тест может ссылаться на несколько целевых
элементов. Поддерживаемые явные противоречия отклоняются детерминированно.
Точный дубликат определяется по нормализованным предусловиям, входам,
шагам и ожидаемому результату независимо от названия и идентификатора.
Семантические дубликаты, согласованность с требованием и достаточность
спецификации проверяются отдельным запросом к LLM для каждого кандидата.
Повторная проверка той же моделью не независима статистически и не доказывает
корректность: результаты обязательно проверяются пользователем.

Предложения получают ID GEN-..., источник «сгенерированный», статус
«ожидает проверки». Нажмите строку предложения для просмотра полного JSON.
Кнопки принятия/отклонения доступны здесь уже на этапе 5; редактирование
сценариев появится на этапе 6. Непринятые и отклонённые сгенерированные тесты
не участвуют в матрице и подтверждённом покрытии. После принятия теста
повторите анализ покрытия и проверьте новые связи. Само принятие теста
не увеличивает процент покрытия. Повторный анализ сбрасывает прежние
подтверждения связей согласно предупреждению этапа 4.

Под таблицей находится журнал: режим, модель, новые ID, обоснования проверки,
причины отклонения/дублирования и целевые элементы без новых предложений.
Пустой/частичный результат отражается в журнале, не считается полным набором.
При ошибке структуры или ссылок, отказе HTTP, отмене проект не меняется;
обычное отклонение кандидата проверкой записывается и позволяет проверить
остальные предложения. Требование CRC не задаёт поведение при Instance != CRC:
такой ожидаемый результат не следует генерировать.

Генерация и проверка работают в фоне. «Отменить текущую операцию» действует
после текущего HTTP-запроса. Во время работы изменение проекта блокируется.
Число запросов: один на требование с целевыми элементами плюс по одному
на каждого структурно корректного кандидата, не отброшенного ранее.
Данные и журнал пока только в памяти. Функциональные проверки используют
подменённые ответы сервера; настоящий Ollama проверьте на Windows.

### Проверка демонстрации CRC

Для текущего проекта с подтверждёнными 4/4 выберите дополнение: ожидается
«Генерация не требуется», 0 новых тестов, покрытие остаётся 100%.
Для первоначального набора перезапустите приложение, импортируйте только
requirements.txt, выделите элементы и запустите первоначальную генерацию.
Проверьте полученные предложения, примите подходящие, затем выполните
анализ покрытия и подтвердите обоснованные связи.
