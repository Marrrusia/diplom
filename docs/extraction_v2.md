# Выделение требований 0.2.0

Версия заменяет эвристическое выделение предыдущих исправлений. Она не
ограничивает требования демонстрационными именами, фиксированными русскими
фразами или словарём глаголов. Универсальная правильность не заявляется.

## Механизм

1. Программа строит каталог исходных фрагментов с точными координатами.
2. LLM предлагает предикаты шести категорий, локальные ID, источники и связи
   с истинными/ложными условиями. Смысл, атомарность и область условий определяет
   модель, а не регулярное выражение.
3. Проверяются JSON, ссылки, уникальность, типы зависимостей и отсутствие циклов.
   Цитаты восстанавливаются из исходника. Новые кодовые имена и числа служат
   сигналом проверки, а не поводом переписать источник.
4. Отдельный запрос LLM проверяет смысловое соответствие, пропуски, категории,
   составные предикаты, отрицания, применимость и достаточность спецификации.
   Эксперт обязан оценить каждый источник и каждый предложенный элемент.
5. Спорные предложения с допустимыми источниками сохраняются с причинами и
   флагом `analysis_blocked`. Они не участвуют в покрытии и целях генерации.
   Кандидаты с неизвестными источниками сохраняются целиком в замечаниях.
   Программа не придумывает им цитат и не достраивает элементы по шаблонам.

Автоматическая достройка режимов, разбиение по русским глаголам и распознавание
ветвей по ограниченному синтаксису удалены вместе с модулями `atomic_elements`,
`branch_context`, `element_grounding`, `extraction_checks`. Предложения об
отсутствующем поведении не удаляются по совпадению фразы: они остаются видимыми
для исправления/отклонения по заключению экспертизы.

Ошибка разбора одного требования не отменяет остальные результаты. Его прежние
элементы остаются видимыми, но блокируются. Если не разобрано ни одно требование,
исходный проект сохраняется. Отмена всегда сохраняет исходный проект. Повторное
выделение сбрасывает прежнее покрытие и привязки тестов к элементам.

## Проверка пользователем

В таблице элементов есть столбец «Допуск к анализу». Прочитайте замечания,
исправьте описание, категорию, цитату и условия, затем примите либо отклоните
предложение. Сначала проверьте обязательные условия действий. Принятие снимает
блокировку; замечания остаются. Отклонение не засчитывается как покрытие.

«Добавить элемент вручную» открывает редактор пропущенного аспекта. Отмена формы
не меняет проект; сохранённое предложение требует принятия. После сверки всех
аспектов используйте «Подтвердить сверку полноты требования» с обоснованием.
Команда требует принятия либо отклонения всех предложений и фиксирует ручное
решение отдельно от мнения модели. Последующие правки снова требуют сверки.

Статистика и XLSX показывают блокировки и неподтверждённую полноту. Процент
относится только к доступным выделенным элементам, а не ко всем фактическим
аспектам текста. Спорные предложения остаются на листе Elements. Новые поля
сохраняются в SQLite; старые проекты загружаются со значениями по умолчанию.

Ограниченные проверки покрытия и генерации остаются подсказками. В генерации
эвристика больше не отвергает кандидат до смысловой проверки: замечания
передаются валидатору и сохраняются в журнале. Тесты не принимаются автоматически.

## Корпус и прогон настоящей модели

`examples/validation_corpus.json` содержит 12 новых требований с иллюстративными
эталонами: прерывания, биты регистров, сроки, насыщение счётчика, циклы, состояния
без оборота «в режиме», вложенные условия, арифметику, границы, запрет DMA,
сбросы и научную запись интервалов. Это не исчерпывающий эталон полноты.

Запуск через установленную модель Ollama:

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_extraction.py --model ИМЯ_ВАШЕЙ_МОДЕЛИ --output work\model-evaluation.json
```

OpenAI-совместимый локальный сервер:

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_extraction.py --provider openai --base-url http://localhost:1234/v1 --model ИМЯ_ВАШЕЙ_МОДЕЛИ --output work\model-evaluation.json
```

Необязательный ключ берётся из `REQTEST_API_KEY` и не сохраняется в отчёте.
Эталоны не передаются настоящей модели. JSON содержит исходник, эталон, результат,
диагностику и время. Сверьте предикаты, отрицания, условия, границы/единицы,
пропуски и добавленные факты вручную. Успешный разбор JSON не измеряет качество.

Для проверки протокола без сервера:

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_extraction.py --fixture --output work\fixture-evaluation.json
```

Здесь ответы подменены, что явно отмечается в отчёте. 12/12 означает выполнение
операций, а не точность модели.

## Ограничения

Два запроса одной модели могут повторить одну ошибку. Наличие цитаты не доказывает
правильность описания; различие имён/чисел может объясняться эквивалентной записью.
Неоднозначность решает человек. Большим требованиям нужен достаточный контекст
модели; пакетная обработка и разбиение с сохранением межтребовательных связей
не реализованы. Вызовов LLM стало больше: выделение и экспертиза каждого
требования с ограниченными повторами при ошибках контракта. Реальные качество,
скорость и вместимость контекста нужно измерить на выбранной модели и оборудовании.
