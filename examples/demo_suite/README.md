# Демонстрационный набор для проверки приложения

Учебные требования и тесты, не спецификация настоящего устройства.
6 требований, 21 тест, 31 эталонный аспект для пяти конкретных требований.
У шестого требования нет достаточной спецификации для конкретных ожидаемых
результатов. Эталон предназначен для человека и не импортируется как ответ LLM.

## Файлы

- requirements.txt / .docx / .xlsx — один и тот же набор требований.
- test_cases.csv / .xlsx — один и тот же набор тестов.
- expected_results.xlsx — ReferenceElements, ExpectedTests, SpecificationGaps.
- expected_results.json — машинно-читаемый эталон для ручной сверки.
- small_sets/ — по одному требованию и его тестам для более быстрой проверки.
- invalid_unknown_requirement.csv / invalid_duplicate_id.csv — намеренные ошибки импорта.

Импортируйте только один формат требований и один формат тестов: не загружайте
TXT, DOCX и XLSX вместе, иначе идентификаторы продублируются.

## Что проверять

| Требование | Тесты | Ожидаемая проверка |
| --- | --- | --- |
| DEMO_RANGE_001 | 6 | 0, 50, 100 допустимы; -1 и 101 возвращают ошибку без изменения поля; BAD противоречит требованию |
| DEMO_MODE_002 | 3 | STANDBY и ACTIVE/готовый ADC; ожидаемый STATUS_TIMEOUT при ADC_READY=0 не задан |
| DEMO_LOOP_003 | 5 | Успех на первой/третьей попытке, три неудачи, неполная проверка статуса, ошибочные четыре вызова |
| DEMO_TIME_004 | 3 | 9 — без вызова; 10 и 11 — один PollSensor без аргументов; сброс таймера не предполагается |
| DEMO_MASK_005 | 3 | 0xA5/0x3C дают 0xAC; проверка только младших битов неполна; один точный дубликат |
| DEMO_AMBIG_006 | 1 | Нельзя подтвердить выдуманные 5 мс и ERR_INVALID_COMMAND |

Статус «частичное покрытие» в эталоне относится к тесту в целом и не является
четвёртым состоянием матрицы приложения. Его отдельные аспекты могут иметь
«покрыт», «не покрыт» или «требует проверки». ID RG_*/MD_*/LP_* и другие в эталоне
— условные идентификаторы человека; сопоставляйте с элементами приложения по
смыслу, а не по буквальному ID.

Граничные примеры не доказывают проверку всех значений диапазона. Успешный
путь цикла не доказывает все его пути. Формулировки должны учитываться при
ручном подтверждении отдельных связей. Число и разбиение элементов LLM могут
отличаться от эталона: это повод проверить смысл, а не механически отклонять
другой способ разбиения.

## Рекомендуемый порядок

1. Начните с small_sets/DEMO_RANGE_001, затем отдельно LOOP, MODE, TIME и MASK.
   Так локальная модель не будет сразу выполнять большой объём запросов.
2. «Файл → Новый проект». Импортируйте requirements.txt выбранного малого набора.
3. Выделите элементы и сравните с листом ReferenceElements общего эталона.
4. Импортируйте соответствующий test_cases.csv. Колонки названы как поля модели,
   но всё равно проверьте сопоставление. Запустите покрытие.
5. Для каждой пары проверьте обоснование, условия, действия и результат.
   Не принимайте плохой сценарий только потому, что модель уверена.
6. Сравните с ExpectedTests. Плохой тест может не покрывать один аспект,
   но содержать допустимую проверку другого; оценивайте пары отдельно.
7. После ручной проверки выполните дополнение покрытия. Оно не должно повторять
   уже имеющиеся сценарии или выдумывать новые исходы.
8. Сохраните SQLite и XLSX с именем соответствующего набора.
9. После малых наборов проверьте все 6 требований вместе: связи не должны
   перескакивать между разными requirement_id, статистика должна совпадать с матрицей.

Число запросов покрытия равно сумме «элементы × тесты» каждого требования.
Полный набор может работать несколько минут и дольше на CPU. Прогресс виден
в строке состояния, отмена действует после текущего запроса.

## Первоначальная генерация

Создайте новый проект и загрузите только требования выбранного малого набора.
Выделите элементы, затем выберите «Первоначальный набор». Проверьте сценарии
по эталону. Для неоднозначного требования ожидается сообщение о недостаточности
спецификации, а не выдуманные время, ответы или список команд.

Для MODE при ADC_READY != 1 нельзя вводить STATUS_TIMEOUT как поведение
из требования. Для TIME нельзя предполагать автоматический сброс elapsed_ms.
Для MASK тестовые константы 0xA5/0x3C — выбранные входы, а результат 0xAC
получен по явно заданной формуле. Для ACTIVE значение 42 задано как результат
заглушки ReadADC, оно не объявляется константой требования.

## Дубликат и ошибочные файлы

TC_MASK_DUPLICATE повторяет TC_MASK_GOOD с другим ID/названием. Импорт разрешает
разные ID; генератор должен избегать такого повтора. Повторные тесты не увеличивают
процент сверх покрытия тех же элементов.

После загрузки требований попробуйте отдельно импортировать файлы invalid_*.
Оба импорта должны быть отклонены целиком, прежние данные должны сохраниться.
Эти файлы не включайте в нормальный рабочий импорт.

## Известные ограничения проверки

Детерминированная проверка точных токенов консервативна: числовой пример 50
не содержит буквально границы 0/100; обозначение 0x0C отличается от 0x0F.
Приложение может показать «требует проверки» даже для допустимого аспекта.
Проверяйте математику/смысл вручную и указывайте собственное обоснование.

Набор проверен настоящими импортёрами и моделями данных. Ответы реального
Ollama на этих новых текстах не получены в облачной среде. Не обещается
фиксированный процент, определённое число ответов или отсутствие ошибок LLM.
